Setting up the database — do it yourself, free
No developer, no server, no monthly cost. About an hour, mostly waiting.
Why this works without a developer
Normally "you need a backend" means someone writes and runs server software. Supabase gives you the two hard parts already built — a shared database and proper sign-in with hashed passwords — and your website talks to it directly. The security lives in rules stored in the database, which is why nobody can cheat it from the browser. Your job is to create the project and paste in the rules. That is genuinely all.
Step 1 · Create the project (10 minutes)
  1. Go to supabase.com and sign up. The free tier is enough for hundreds of parents — no card needed.
  2. Click New project. Name it psle-toolkit.
  3. Set a database password. Write it down somewhere safe — you cannot recover it, only reset it.
  4. Choose the region closest to Botswana — likely eu-west or South Africa if offered. Closer means a faster app.
  5. Click create, then wait. It takes a couple of minutes to build.
Step 2 · Paste in the rules (5 minutes)
  1. In your project, click SQL Editor in the left sidebar, then New query.
  2. Open the file supabase-setup.sql from this project. Select all of it, copy it, paste it into the editor.
  3. Click Run. You should see "Success. No rows returned" — that is what success looks like here.
Two common trips. Copy the file's contents, not its name — pasting supabase-setup.sql gives a "syntax error at or near supabase". And if the file is ever updated, paste the new version and run it again: it is written to be safe to re-run as many times as you like.
That one file created five tables and — more importantly — the rules that make this safe: a visitor can place an order but can never mark one as paid, and cannot read the orders list at all. Only you, signed in as admin, can verify a payment.
Step 3 · Connect the website (2 minutes)
  1. In Supabase go to Settings → API.
  2. Copy the Project URL and the anon public key.
  3. Open supabase-config.js in this project and paste them between the quotes. Save.
  4. Now go to Authentication → Providers → Email and switch Confirm email OFF. See the box below for why.
Why switch off email confirmation
Supabase starts with it on, which means nobody can sign in until they click a link in an email. For your parents that is one more thing to go wrong, and your main way in is the access code anyway — not email. Leaving it on also blocks Step 4: your own account will not exist in the system until you click the email, and the admin command will report 0 rows, which looks like the SQL failed. Turn it off now; you can revisit it later if you ever need email verification.
The one thing you must not get wrong
There are two keys on that page. The anon public key is safe in your website — it is designed to be seen by every visitor, and the database rules stop it doing any harm. The service_role key ignores every rule you just set up. Never put it in the website, never paste it into a chat, never email it. If it ever leaks, click Reset on that page immediately.
Step 4 · Make yourself the admin (5 minutes)
  1. Open your own website and go through Get access once, using your real email and a password you will remember. This creates your account.
  2. Back in Supabase, open SQL Editor → New query and run this, with your email in place of the example:
insert into profiles (id, is_admin)
select id, true from auth.users
 where email = 'you@example.com'
on conflict (id) do update set is_admin = true;
Check it worked by running select u.email, p.is_admin from profiles p join auth.users u on u.id = p.id; — your row should say true. From now on the admin dashboard recognises you by your login, not a PIN anyone could guess.
Step 4b · "Sign in with Google" — optional, skip for the pilot
Google sign-in is switched off, and the button stays hidden until you turn it on — so nobody sees a control that cannot work. You do not need it: parents sign in with email and password, and children use the access code. Only do this if parents ask for it.
  1. At console.cloud.google.com, create a project (free).
  2. Open APIs & Services → OAuth consent screen. Choose External, fill in the app name and your email, save.
  3. Go to Credentials → Create credentials → OAuth client ID, type Web application.
  4. Under Authorised redirect URIs add exactly this, then create:
https://ovoioaarepuiczsprvlx.supabase.co/auth/v1/callback
  1. Copy the Client ID and Client secret.
  2. In Supabase go to Authentication → Providers → Google, switch it on, paste both, save.
  3. Reload your sign-in page. The Google button appears on its own — nothing to edit in the site.
Step 5 · Put the site online (20 minutes)
Parents cannot use files sitting on your laptop. Free hosting, no card:
  1. Download this project as a folder.
  2. Go to netlify.com, sign up, and choose Deploy manually — literally drag the folder onto the page.
  3. You get a web address like psle-toolkit.netlify.app. Share that with parents. HTTPS is automatic, which matters because you are handling children's names and parents' numbers.
  4. To update the site later, drag the folder again. Nothing else to do.
Step 6 · Test it properly before charging anyone
Use two devices — your laptop and your phone. This is the test that proves the whole thing works:
On your phone
Buy a package. Write down the code. Try to sign in with it — it must refuse you, saying the payment is not confirmed. If it lets you in, stop and tell me.
On your laptop
Open the admin dashboard. The order from your phone must appear — this is the thing that was broken before. Click Mark paid.
Back on your phone
Enter the code again. It should now let you in, showing only the subjects that package covers. Then revoke it on the laptop, reload the phone — access should disappear.
What this still does not do
  • Payments are still confirmed by hand. A parent pays by Orange Money or MyZaka, WhatsApps you the proof, you click Mark paid. That is fine up to roughly thirty parents and costs nothing.
  • The question banks are public files. Anyone determined can download them. Protecting them properly is possible later, but it is a commercial nicety, not a safety problem — do not spend money on it now.
  • Password reset needs email set up in Supabase (Authentication → Email templates). Until then, reset a forgotten password yourself from the dashboard.
  • Free tier pauses an unused project after a week of no activity. One visit wakes it. Once real parents are using it daily this stops happening.
If something goes wrong
Leave supabase-config.js blank and everything reverts to working on one device, exactly as before — so you can never break the site beyond repair. In Supabase, Logs in the sidebar shows every failed request and why. Bring me the error text and I will fix it.
