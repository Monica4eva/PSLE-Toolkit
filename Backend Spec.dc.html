PSLE Prep Toolkit — Backend Specification & Developer Handoff
What exists, what must be built before taking payment, and how to build it
Read this first
The front end is complete and working: six question banks (2,000+ questions), nine learner modules, a purchase flow, an access gate, an upgrade path and an admin dashboard. Every business rule is enforced in the browser only, with data in localStorage. That is why this document exists. The single blocking defect is that access state is per-device: the owner can verify a payment on her laptop and the parent's phone will never know. Nothing else on this list matters until that is fixed.

2 · Security defects, in priority order
# Defect Consequence & fix
1Access state is per-deviceA paying parent cannot be granted access remotely. Blocks launch entirely. Fix: server-side database as the single source of truth.
2Gate is client-sideDev tools can forge a verified record. Fix: server validates every session; questions served only to authorised sessions.
3Plain-text passwordsReal parents' passwords readable in browser storage. Legally and ethically unacceptable. Fix: bcrypt/argon2 server-side; never store or transmit plain text.
4Admin PIN in client codeDefault 2026, visible in source, no rate limiting. Fix: real admin account, server-authenticated, with an audit log.
5Unlimited code sharingOne P300 code could serve a whole village over WhatsApp. Fix: bind each code to a device limit (3 suggested); count and refuse beyond it.
6Manual payment verificationOwner must read every WhatsApp proof by hand; does not scale past ~30 parents. Fix: payment-provider webhooks that auto-verify on reference match.
7Google sign-in simulatedLabelled as a demo, so nobody is misled, but it is not real auth. Fix: Google OAuth 2.0 with server-side token exchange.
8Progress not backed upClearing the browser wipes a child's stars and history. Fix: sync progress per learner to the server.
3 · Recommended architecture
The cheapest path that solves defects 1–3 is a managed backend-as-a-service rather than a custom server. Supabase (Postgres + hosted auth + row-level security, generous free tier) is the recommendation: it gives hashed passwords, Google OAuth and a shared database without writing an auth system. Firebase is an equivalent choice. A custom Node/Express + Postgres build is only worth it if the developer already has that stack running.
Keep the question banks as static files
The 18 bank-*.js files never change per user, so they do not belong in a database. Serve them from the CDN and gate the app shell, not each question. If protecting the content itself matters commercially, move them behind an authenticated endpoint later — but note that anything the browser can render, a determined user can copy. Do not spend the pilot budget on this.
4 · Data model
Five tables. Field names match the shapes the front end already builds, so the migration is mostly swapping localStorage reads for API calls.
Table Columns
accountsid, email (unique), password_hash, provider (password|google), parent_name, phone, role (parent|admin), created_at
ordersid, account_id, plan (single|bundle|full), price, subjects (array), method, reference (unique), status (pending-verification|verified|revoked), verified_at, verified_by, created_at, expires_at
access_codescode (PK, format PSLE-XXXX-XXXX), order_id, learner_name, standard, device_limit (default 3), status
devicesid, code, fingerprint, first_seen, last_seen — enforces the device limit
progressid, code, subject, answered, correct, stars, checklist (json), updated_at
5 · Endpoints
Endpoint Behaviour
POST /ordersCreates account (if new) + order + access code. Status always pending-verification. Returns code and payment reference. Never returns a usable session.
POST /auth/loginEmail + password → session token. Rate-limit to 5 attempts per 15 min per IP.
POST /auth/googleReal OAuth token exchange, server-side.
POST /access/redeemBody: code + device fingerprint. Returns {authorised, subjects, learner} only if status is verified and the device count is under the limit. This is the security boundary.
GET /access/sessionRe-validates on every app load. Replaces the current client-side status re-check, so a revoked code loses access within one refresh.
POST /admin/orders/:id/verifyAdmin only. Sets verified, stamps who and when. Mirrors the existing "Mark paid" button.
POST /admin/orders/:id/revokeAdmin only. Sets revoked; all sessions for that code die on next validation.
POST /webhooks/paymentProvider callback. Verify signature, match on reference, auto-verify the order. Idempotent — the same event twice must not double-grant.
PUT /progressUpserts a learner's progress. Debounce client-side; this fires often.
6 · Front-end changes required
The UI does not need redesigning. Each change below swaps a storage call for a network call; the screens, copy and states already exist.

7 · Build order
Phase 1 — Make a paid pilot possible (defects 1–4)
Supabase project, the five tables, hashed-password auth, /orders, /access/redeem, /access/session, admin verify/revoke behind a real login. Payment stays manual — the owner confirms a WhatsApp proof and clicks Mark paid, but now it works on every device. This is the minimum to charge money.
Phase 2 — Reduce the owner's workload (defects 5, 6, 8)
Payment webhooks for auto-verification, device limits, progress sync. Needed once there are more parents than the owner can verify by hand.
Phase 3 — Polish (defect 7 and beyond)
Real Google OAuth, password reset by email, parent dashboard showing the child's progress, per-topic analytics for the owner.
8 · Non-negotiables for whoever builds this
  • Never trust the client for authorisation. The browser may request; only the server decides.
  • Never store a password in plain text, anywhere, at any stage — including logs.
  • Remove the demo bypass (PSLE-2026-DEMO) and the default admin PIN before launch.
  • HTTPS everywhere; children's names and parents' phone numbers are personal data.
  • Make the payment webhook idempotent and signature-verified.
  • Collect only what is needed. Learner first name and standard is enough; no birth dates, no addresses, no photographs.
  • Keep an audit log of who verified or revoked which order — this is money.
